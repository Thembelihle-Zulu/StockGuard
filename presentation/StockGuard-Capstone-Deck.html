Livestock insurance that verifies what it insures.

Self‑service cover for South African farmers — priced and paid out on a vet‑verified animal value, not a number typed into a form.

Problem & scope
1:00–3:00
The problem

An animal dying is a financial cliff‑edge — and cover doesn't reach the farmers who need it.

South Africa's foot‑and‑mouth outbreak has hit 210,000+ cattle across 90+ dairy farms since 2024; beef exports fell 26% and recovery is estimated at up to four years. Existing livestock insurance is priced for large commercial operations and trusts a self‑reported animal value — which drives mispricing and real fraud exposure.

Who it's for
  • Small‑scale farmers — simple, affordable
  • Commercial farmers — larger, higher‑value herds
  • Platform admins — insurer staff who verify
Scope
  • Registration → verification → underwriting → claims
  • Theft cover — nothing left to inspect
  • Live payment gateway — mocked by design
  • Multi‑policy accounts

Architecture
3:00–5:00
Architecture & the decision that matters most

Every protected route derives the farm from the JWT, never from the request — a client can't act on another farm by editing a URL or body. Cross‑farm reads return 404, not 403, so the API never confirms another farm's records exist.

A claim pays out only if all three server‑enforced checks pass
The farm's policy status is Active
That specific animal's inspection is Approved
Claim amount ≤ the admin‑approved insured value
Mocked on purpose: payment — data model already matches a real gateway

Engineering quality
11:00–13:00
Security, validation, testing — and one real challenge
Security & validation
  • JWT ownership check on every protected route
  • Passwords hashed (werkzeug); login can't be used to enumerate accounts
  • Yup client‑side, mirrored by server checks that don't trust the client — claim cap, status‑transition rules, ISO‑date parsing with a 400
Testing — manual, and honest about it
  • Every workflow walked by hand against a seeded database
  • Three demo farms staged at three journey points — success, empty and failure states all reachable
  • No automated suite yet — the claim‑eligibility gate is where I'd start
The challenge I solved

The claim gate was already correct server‑side — but the UI let a farmer fill in the entire claim form before the 403 came back. Correct isn't the same as usable. I added a pre‑check that tells the farmer exactly what's missing — no policy, policy not active, identity not on file — before the form opens.

Reflection
14:00–15:00
Personal reflection & next goal
Key learning
The gap between “the feature exists” and “the feature is usable” — my claim gate was server‑side correct, but a farmer only hit the 403 after filling the whole form.
Growth — concrete
At the start I could build a form that posts to an API. By the end I designed and enforced a three‑layer authorization chain server‑side, and corrected my own pricing model mid‑build when the numbers didn't add up.
Strength
Systematic bug‑hunting — found a silent console.log() && setState that never set state, and a file‑casing bug that worked on Windows and would break a Linux build.
Development area & action
Automated testing. This build has none — every check was manual under deadline pressure. It got me here but it doesn't scale.
What I'd do differently
Write tests as each feature lands, not as one verification pass at the end — most bugs I found had been sitting in the code for a while.
Next specific goal
Write my first real test suite, starting with the three‑layer claim‑eligibility logic — the rule most likely to break silently later.
