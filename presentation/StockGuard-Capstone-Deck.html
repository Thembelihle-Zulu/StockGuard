Problem & scope
1:00–3:00
The problem

An animal dying is a financial cliff‑edge — and cover doesn't reach the farmers who need it.

South Africa's foot‑and‑mouth outbreak has hit 210,000+ cattle across 90+ dairy farms since 2024; beef exports fell 26% and recovery is estimated at up to four years. Existing livestock insurance is priced for large commercial operations and trusts a self‑reported animal value — which drives mispricing and real fraud exposure.

Who it's for
  • Small‑scale farmers — simple, affordable
  • Commercial farmers — larger, higher‑value herds
  • Platform admins — insurer staff who verify
Scope
  • Registration → verification → underwriting → claims
  • Theft cover — nothing left to inspect
  • Live payment gateway — mocked by design
  • Multi‑policy accounts

Architecture
3:00–5:00
Architecture

Three layers — each chosen for a reason.

React (with Vite)
The farmer side is a multi‑step journey and the admin side is a data‑heavy console — a component model keeps both maintainable, and Vite gives instant feedback while building. MUI + Formik/Yup for accessible forms that validate before they submit.
Flask REST API (Python)
Small and explicit: one blueprint per resource keeps the API readable and the business rules easy to find. SQLAlchemy for safe, parameterised queries; Flask‑JWT‑Extended for stateless auth where every route derives the farm from the token.
Microsoft SQL Server
The domain is naturally relational — farm → animals → inspections → claims, plus policies and payments — and it moves money and policy state, so foreign keys, constraints and transactions doing the enforcing matters more than raw flexibility.

Engineering quality
11:00–13:00
Security, validation, testing — and one real challenge
Security & validation
  • JWT ownership check on every protected route
  • Passwords hashed (werkzeug); login can't be used to enumerate accounts
  • Yup client‑side, mirrored by server checks that don't trust the client — claim cap, status‑transition rules, ISO‑date parsing with a 400
Testing — manual, and honest about it
  • Every workflow walked by hand against a seeded database
  • Three demo farms staged at three journey points — success, empty and failure states all reachable
  • No automated suite yet — the claim‑eligibility gate is where I'd start
The challenge I solved

The claim gate was already correct server‑side — but the UI let a farmer fill in the entire claim form before the 403 came back. Correct isn't the same as usable. I added a pre‑check that tells the farmer exactly what's missing — no policy, policy not active, identity not on file — before the form opens.

Reflection
13:00–15:00
Personal reflection

What the training changed about how I work.

Familiar ground, new tools
I'd built back ends before in another language, so REST APIs, routing and working with a database were ideas I already had. Picking up Python and Flask was new syntax over familiar concepts — not starting from zero.
A shift I didn't expect
I went in not expecting to enjoy frontend work. React changed that — thinking in components, with hooks and state, made building the UI feel structured rather than fiddly.
The hardest part
Deploying to AWS — the number of services and manual console steps, and how easy it is to get one wrong.
What clicked, and what's next
Deploying by hand was like cooking from memory every time — miss a step and it's wrong. Terraform is writing the recipe down: the whole stack in code, so it runs the same way twice. Next I want to go deeper on React patterns and Terraform modules.
